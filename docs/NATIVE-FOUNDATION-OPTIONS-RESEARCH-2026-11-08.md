# Foundation decision: Venus, PersonaPlex and full fine-tuning

8 November 2026. Research-only review; no downloads, jobs, API calls or weight changes performed by this review. Read alongside the current product goal, the7November reasoning/capacity strategy and the8November complete training readout. This note updates the foundation decision; it does not authorize replacing a running job or claim a model is qualified.

## Recommendation

**Do not commit the next substantial run to Venus by default, and do not make full fine-tuning the default remedy. Run one bounded native comparison of untouched PersonaPlex against the retained Venus evidence, while checking the unmodified Venus speech contract. Choose the foundation from spoken product behaviour, then train the chosen model with a retention-controlled recipe.**

PersonaPlex is the strongest immediate alternative to test for this English voice product. That is a priority for measurement, not a finding that it has better reasoning. Venus remains a credible incumbent because it already has a native delegation protocol and a supported audio/text architecture. MiniCPM-o4.5 is a useful third control if the upstream-versus-Venus distinction remains material. A large catalogue of untested models would delay the decision.

There are **three** competing sources of failure: the released foundation, our adaptation, and our inference/voice/runtime configuration. Their effects must be separated. A released model tested through our modified speech runtime is not a pristine upstream runtime baseline.

## Exact lineage and why Qwen does not disqualify Venus

Venus is **not** a PersonaPlex fork or a text-only Qwen model with an ordinary external ASR/TTS cascade. The authors adapted the already multimodal MiniCPM-o4.5 foundation. Its9B architecture has a Qwen3-8B language backbone, Whisper-Medium audio features, and native S3 speech-token generation followed by a streaming flow decoder. Generated language hidden states participate in speech conditioning. The model predicts listen/speak/turn decisions in one-second streaming units while perception continues. Native duplex is a property of the trained complete system, not a requirement that its language backbone was never pretrained on text. [Venus paper, architecture](https://arxiv.org/html/2609.13814v1#S4).

Importantly, Venus's own published post-training recipe updates **only the Thinker** and keeps the acoustic decoder frozen. Thus, our use of a frozen TTS decoder is not, by itself, proof that the method is invalid. Language-side changes can improve or damage speech conditioning. The paper describes mixed understanding, duplex and delegation training with sparse response/control supervision; it does not show that any small language-only dataset will retain speech quality. [Venus paper, training recipe](https://arxiv.org/html/2609.13814v1#S4.S6).

The original choice was consequently reasonable: an existing native duplex model plus explicit asynchronous delegation is close to the intended architecture. The remaining question is whether its measured English speech, reasoning, runtime and adaptation behaviour make it the best engineering starting point. Neither its Qwen ancestry nor its paper's benchmark claims settles that question. The first-party repository describes a separate background Harness and a foreground model that reintegrates results; native request emission is not the same as successful execution or faithful spoken delivery. [Official Venus repository](https://github.com/inclusionAI/Realtime-Venus).

PersonaPlex follows a different lineage: pretrained Moshi/Moshiko, whose language backbone is Helium, followed by NVIDIA's role/voice post-training. It uses Mimi audio encoding/decoding and temporal/depth transformers with concurrent user and assistant audio streams at24kHz. Text and voice prompts provide persona and speaker conditioning. NVIDIA reports mixing synthetic task-oriented speech with1,217 hours of real Fisher conversations for the released model. These features make it a strong natural-English-interaction candidate, not a proven stronger mathematical reasoner. [NVIDIA project and architecture](https://research.nvidia.com/labs/adlr/personaplex/), [released model card](https://huggingface.co/nvidia/personaplex-7b-v1).

Moshi itself also starts from a text-language foundation and then learns speech-text alignment and parallel audio streams. Its authors report160ms theoretical/200ms practical latency under their setup; those are not our PersonaPlex/GH200/browser measurements. The base Moshi card explicitly limits complex-task/tool capabilities. Native duplex does not imply frontier reasoning. [Moshi paper](https://arxiv.org/abs/2410.00037), [Moshi card](https://huggingface.co/kyutai/moshiko-pytorch-bf16).

## One short comparison that can change the decision

Use unchanged synthetic user audio and a frozen, compact cohort with direct arithmetic/context, technical explanation, clarification, named-entity task transfer, silence/cue release, interruption, pending work, cancellation and grounded result use. Keep all cases, original gates and input hashes; save the raw waveform, generated text, timing and task events. Use a few blinded English/British listening samples to select a voice, without treating a good sample as whole-cohort acceptance.

Run PersonaPlex through its released **native audio** interface and documented assistant/voice prompt. Do not feed it Venus's ChatML/one-second token protocol or load an old rejected project adapter and call that the base. Where a released model has no matching tool channel, report that limitation; initially separate its comprehension/conversation test from tool-plumbing work. Measure semantic correctness of the task description and later actual backend completion separately. Raw text-token correctness alone is insufficient for a Moshi speech model.

In parallel within the same bounded decision, inspect Venus under the pinned official inference contract, using the bundled reference/default first and an explicitly permitted English reference as a separately labelled condition. Current GitHub Audio example calls `prepare(prefix_system_prompt=...)`; the Hugging Face Audio example explicitly supplies `HT_ref_audio.wav`. The sources do not certify that this file is English/British. Both use one-second input chunks,10seconds trailing silence and timeline-positioned output. The examples clip at final WAV export: retain **preclip** peaks/raw chunks for our checks and do not import that clipping as a way to pass our peak gate. [Official Audio example](https://raw.githubusercontent.com/inclusionAI/Realtime-Venus/main/frontend/Realtime-Venus-Audio/audio_duplex_chat.py), [official Audio guide](https://raw.githubusercontent.com/inclusionAI/Realtime-Venus/main/frontend/Realtime-Venus-Audio/README.md), [model-card duplex example](https://huggingface.co/inclusionAI/Realtime-Venus#83-duplex-chat).

The existing intact-reference-cache diagnosis remains valid and should not be reopened merely because a per-frame argument is absent. The check above distinguishes the complete released path from our combined completion/action/British-reference path. If the pristine path is clear, fix our integration before training around it. If both paths share speech defects, favour the foundation with better actual speech/latency and train missing control/reasoning skills there.

Selection should be lexicographic: intelligible stable English speech and usable latency first; adequate basic reasoning and honest uncertainty next; controllable duplex behaviour and feasible task-context integration next. A weighted average that lets better text accuracy conceal gibberish is inappropriate. Use the published papers to choose contenders, and our measurements to choose a base. Stop the comparison when it changes the branch; do not keep evaluating every new model release.

## Is full fine-tuning possible, and when is it justified?

Yes. LoRA learns a constrained update while keeping original parameters frozen; full fine-tuning directly updates the selected pretrained parameters. Neither supplies knowledge without data, and neither guarantees retention. The LoRA paper does not claim that full fine-tuning is always superior. Our698M trainable LoRA is already substantial; its failure is not a proof of insufficient parameter count. [Original LoRA paper](https://arxiv.org/abs/2106.09685).

There is an official practical route for the Moshi family: Kyutai's example sets `full_finetuning: true`, `lora.enable: false` and `save_adapters: false` for full training, and documents multi-GPU launch. PersonaPlex's hybrid voice/text prompts, weights/configuration and loss conventions still require compatibility checks; this is not permission to run a Moshi example unchanged on PersonaPlex. The official data format uses separate stereo user/assistant speech plus time-aligned transcripts. Its provided LoRA throughput numbers are not full-training or our-data predictions. [Official configuration](https://raw.githubusercontent.com/kyutai-labs/moshi-finetune/main/example/moshi_7B.yaml), [official trainer](https://github.com/kyutai-labs/moshi-finetune).

Define what “full” means before launch. Full language-backbone/temporal-transformer training is different from updating the audio encoder, semantic speech decoder, waveform decoder and every embedding simultaneously. Begin with the component responsible for the measured deficit, keeping the codec/waveform path frozen unless acoustic evidence calls for adapting it. For Venus, changing the language hidden space can affect the frozen speech interface; for Moshi, language and speech prediction are also coupled. An unfreeze-everything experiment is not a shortcut around alignment.

After choosing the base, use a matched adaptation comparison with the same source corpus, supervised-token exposure and frozen evaluation: a broad-adapter control versus a carefully lower-LR full/selected-component branch. Maintain general/native rehearsal, original text/audio objectives and a reference policy/hidden-space retention term where appropriate. Save untouched base, initialization, complete optimizer/RNG/OPAL state and immutable learning checkpoints. Evaluate native speech and reasoning at complete boundaries; checkpoint/early-stop selection uses DEV, while the frozen final cohort remains excluded from training decisions.

For a new full-weight branch, state explicitly whether optimizer state can be mapped; LoRA Adam state cannot simply become full-weight Adam. Preserve the old state and start a declared new optimizer only for newly trained base parameters, rather than pretending there is an exact full-weight continuation. Independently restore the new branch before extending it. If the broad-adapter branch improves and full training loses naturalness/control, do not adopt full training merely for lower CE.

## Isambard compute plan

These are planning estimates, not measured memory admissions. Conventional mixed-precision Adam may use roughly12–18 bytes per trainable weight for weights/gradients/moments/master copies, before activations and temporary tensors. Thus7B full training is approximately84–126GB and8B approximately96–144GB of such state. The exact optimizer/dtypes/offload strategy changes the total; inference fit does not establish training fit. [Memory components](https://huggingface.co/docs/transformers/main/en/model_memory_anatomy).

| Resources in one Slurm job | Sensible role |
|---|---|
|1GH200 | Released native inference comparisons; current broad LoRA; bounded partial/component adaptation. Full7–8B may require heavy offload and is not assumed to fit. |
|2GH200 | First practical full/selected-language-weight branch with state sharding, measured native forward/backward and restore. Preserve effective global batch and native temporal gradients. |
|4GH200 | Use if measured memory or time-to-quality justifies it, rather than spending hours preserving an arbitrary one-GPU constraint. |

FSDP can shard parameters and optimizer state but changes parameter ownership and needs the optimizer constructed after wrapping. Existing OPAL/Adam state and streaming KV-autograd assumptions must be checked against that actual integration; do not place an FSDP wrapper around the current trainer and claim numerical/state equivalence. [PyTorch2.9 FSDP](https://docs.pytorch.org/docs/2.9/fsdp.html).

Use the20,000-GPU-hour award decisively for the selected learning branch and complete evaluation. Keep one scheduler-controlled job at a time, allowing multiple GPUs inside that job, and record actual allocated GPU-hours. No GCP purchases or new external API payloads follow from this recommendation. One useful multi-GPU admission and a sustained learning schedule are preferable to repeated zero-update retries.

## What carries over if PersonaPlex wins

The data concepts, approved original source audio, task/world receipts, failure classifications, evaluation design, runtime invariants and checkpoint discipline remain valuable. Preserve every original fold and inspected holdout boundary. Rebuild native token histories/caches and verify timing/labels under the selected architecture.

Venus Qwen LoRA matrices do **not** transfer meaningfully into Moshi/Helium by copying tensor names or matching dimensions. They are updates in different weight bases, with different tokenizers and audio interfaces. PersonaPlex adapters from our earlier work may only be reused with their exact compatible base and verified lineage; a rejected old pilot is not a new baseline. Context Spanning remains a reusable architectural idea for passing reasoning context/results, not an automatic trained-model conversion.

The prepared text curriculum is portable training material, not a commitment to Venus or proof of native audio qualification. After the comparison, grow verified concept/routing coverage and perform a substantial selected-model training run. Pretraining from scratch, a billion random added parameters, and full unfreezing of all components are unnecessary default steps. The outcome to optimise is correct, natural, low-latency native interaction with reliable reasoning allocation—not model size or an impressive training-loss curve.

### Reuse before rerunning

The7558824 review binds four historical ordinary controls7530265–7530268 and independent ASR7530273–7530276 to the **same input audio hashes, voice/persona/assets, Torch/CUDA and native routing**; all four correct spoken answers had WER0 and first nonzero PCM approximately0.452–0.465s. Reuse their original WAVs, source bindings and transcripts to demonstrate what that earlier adapted model could do, and to avoid rerunning this four-question microtest merely to rediscover that capability. They do not establish an untouched-base score, British voice quality, broad reasoning or microphone latency. Later default/archived-runtime comparisons above show why their4/4 cannot be combined indiscriminately with a later2/4 into a training effect. The complete32 fit and complete20 native/speech reviews are already adequate evidence to reject unchanged saved528; repeat none of those optimizer steps or complete diagnostics simply because they failed.

Data/objective findings also already exist. Four of25 old teacher histories had physically impossible first-word onsets, requiring versioned derived-timing repair/reapproval while keeping original audio/words/receipts and all histories. Reasoning32 included40 real native request-token targets, but their mean coefficient mass within its supplemental balanced-text objective was only approximately0.07–0.28% in request-bearing families. That audit establishes target presence and dilution, **not** whole-gradient attribution or causal proof. Low effective LR2e-7, one exposure, inherited Adam moments, timing/history validity and rare action alignment were concrete hypotheses; neither batch size nor inadequate1.8944M capacity was isolated. ### Why Venus became the working branch—and what remains open

The26 October released Venus diagnostic collected all10 cases and generated correct ordinary core **text4/4** under its own interface, after repeated rejected prior-family pilots. That was useful motivation to explore it, **not a controlled finding of superior spoken reasoning or production suitability**. Both Venus cue-silence cases failed; pending/cancellation were not genuinely exercised, one delegated query altered569→570, independent spoken accuracy remained pending, and92/457 compute chunks exceeded one second. The record explicitly says diagnostic/not qualified/not adopted. [Original Venus complete10 review](NATIVE-VENUS-COMPLETE10-REVIEW-2026-10-26.json).

Therefore previous PersonaPlex work neither proved its foundation incapable nor proved that full fine-tuning is necessary. It established several failed **adaptation recipes**, some confounded by retention omission and runtime sensitivity. Existing reusable data, receipts, native context-span mechanics and failure cases remain valuable. The present next decision should use one focused pristine-runtime/native comparison against released PersonaPlex—not restore a rejected old adapter and call it the base. If a viable foundation still shows learning interference, choose targeted data/rehearsal/objective repair before assuming that random added parameters solve it. A selected language-weight/full-transformer branch is technically reasonable when matched evidence justifies it; preserve codecs/voice paths initially and test full-state/retention behavior, rather than automatically unfreezing every component. The current698M Venus experiments test a different architecture/capacity intervention and cannot retroactively identify the cause of the older1.8944M failures.
