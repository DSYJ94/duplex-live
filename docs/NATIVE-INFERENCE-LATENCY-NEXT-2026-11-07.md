## Test ordinary LoRA folding for inference

The custom `LoRALinear.forward` executes two extra FLOAT32 matrix products, casts and additions on every adapted projection, plus the inherited extra branch where present. The 698M adapter covers all seven projections in 36 layers. This is a concrete **hypothesis** about avoidable inference overhead, not proof that it accounts for the measured slowdown. Training can retain the exact unmerged representation while a disposable serving model folds its learned deltas into the base projection. The original [LoRA paper](https://arxiv.org/abs/2106.09685) discusses adaptation without additional inference latency, and [official PEFT documentation](https://huggingface.co/docs/peft/v0.21.0/package_reference/lora) documents adapter merging to eliminate adapter inference overhead. Our custom module is not PEFT; it needs its own tests.

New opt-in `training/venus/merged_inference.py` creates replacement inference Linear modules, folding both inherited and additional branches in FLOAT32 before casting the effective weight to native storage dtype. It never edits the original base/adapter tensors or checkpoint/Adam/RNG/OPAL state. It rejects trainable/disabled/nonfinite inputs and restores original module objects if a later fold fails. Default inference and the running trainer are unchanged. This is ordinary low-rank algebra, not weight-space surgery or an optimizer update.

**BF16 bit identity is not expected:** the original graph rounds intermediate outputs, while folding rounds weights. A mathematically equivalent real-valued expression does not establish equivalent finite-precision generated tokens or speech. CPU tiny-tensor checks are not GPU/native qualification. Keep this variant experimental and do not use it to resume training.
