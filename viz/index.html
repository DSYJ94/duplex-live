Why is PersonaPlex in the list when it wasn't in the original plan? Because it was released in January 2026 — after the first version of the plan was written. It matters for two reasons: (1) it is currently the best open demonstration of true full-duplex behavior (no VAD, natural barge-in/backchannels), so it is the reference point our Qwen3-Omni fine-tune must match on interactivity; (2) its training recipe — synthetic conversations rendered with open TTS (Chatterbox/Tortoise) — independently validates our synthetic interaction-dynamics factory, the riskiest part of our data plan. Caveat: it stacks three licenses (MIT code, NVIDIA Open Model License weights, CC-BY Moshi base), so it is a research reference, not a deployment base, until the NVIDIA terms are reviewed.

Bottom line: fine-tune Qwen3-Omni 30B-A3B for the intelligence-max duplex model; keep PersonaPlex and MiniCPM-o 4.5 as duplex-behavior references and quick demo paths. Delegate to Kimi API (or a self-hosted open model) behind the async boundary.

1½ · What "full-duplex architecture" actually means — three layers

Resolved 2026-09-14 after comparing GPT-Live and TML's posts: duplex is not one thing. This drives exactly what we modify in Qwen3-Omni (docs/09).
LayerWhat it isArchitectural or data?Our work
A · CapabilityModel ingests new input while generating output. A vanilla LLM structurally cannot — during generation there is no input channel.Architectural sequence format + inference loopTick-loop driver (~200 lines) + interleaved training format + new token embeddings. Weights of the backbone unchanged.
B · PolicyWhen to speak, stay silent, backchannel, barge in, yield.Data learned from overlap/silence statisticsSynthetic factory (Issue #3), silence-loss weighting, retraction training.
C · ClockServing loop feeding 80 ms chunks unconditionally, persistent GPU session state.Systems pure engineeringStreaming session (Issue #5 territory), no VAD anywhere.
So what is "the trick"? Mostly engineering plus tiny new embeddings — not new backbone weights, not adapters in the LoRA sense:
① Serialize the two streams into one causal sequence on the model's own 80 ms grid (AuT encoder emits 1 token / 80 ms; Talker generates 1 codec frame / 80 ms — the heartbeat already matches). Every tick: append one audio token to the KV cache (1-token prefill), decode one emission — a text token (Talker speaks it), <sil> (silence frame), <delegate> (async RPC), or <yield> (flush pending speech on barge-in).
② The root cause of half-duplex is a single gate: generation waits for "user finished", and no new audio enters context mid-response. Remove the gate; causality is preserved because the interleaving is just what gets appended when.
③ New vocab rows (<sil>, timing tokens, <delegate>, <yield>) are the only new weights in Phase 1; the 30B backbone is frozen.
④ Gifts from Qwen's design: the Talker is already text-decoupled (explicit intervention hook), and the model family already inserts timestamps for temporal perception.
Architecture provides the channel, data provides the manners, serving provides the clock.
